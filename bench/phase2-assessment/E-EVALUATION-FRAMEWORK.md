# Echo Intelligence Evaluation Framework V1

任务编号：EC-PHASE2-01 / WP-04  
日期：2026-10-31  
性质：长期智能能力评价体系设计（独立于具体模块实现）

---

## 1. 设计原则

1. **模块无关**：评价维度不与任何模块内部代码结构绑定；测的是行为产出，不是函数存在。
2. **可重复**：每个测试案例固定输入、环境、评分标准，任意时间重跑结果可比。
3. **证据分级**：每项结论必须标注证据层级——`代码存在` / `已接入` / `有测试证据` / `重复验证` / `长期可靠`。禁止混淆。
4. **环境锚定**：模型、提示词、工具权限、环境变化必须记录，避免环境差异冒充能力提升。
5. **反对指标通胀**：不为数字好看制造无意义指标；无法可靠量化的维度明确走人工评审。

## 2. 七个评价维度

| # | 维度 | 评价目标 | 主要度量 |
|---|------|----------|----------|
| D1 | 任务理解 | 准确理解用户目标和约束 | 约束满足率、隐式约束识别率 |
| D2 | 长期记忆 | 保存、检索、复用跨会话信息 | 检索准确率、使用有效率、冲突处理正确率 |
| D3 | 推理规划 | 制定合理多步骤计划并适应变化 | 计划完成率、重规划触发正确率 |
| D4 | 执行可靠性 | 稳定完成实际任务 | 工具调用成功率、任务成功率、幂等保持率 |
| D5 | 失败恢复 | 发现错误并恢复执行 | 故障恢复成功率、错误识别率 |
| D6 | 经验复用 | 将过去经验用于新任务 | 经验引用率、经验有效性（加速/避坑） |
| D7 | 长期稳定性 | 长任务状态与运行连续性 | 状态保持率、上下文漂移率、成本可预测性 |

维度调整规则：审计后允许增删维度，但必须记录调整原因与日期，且调整后旧基线标注"不可直接比较"。

## 3. 指标定义

### 3.1 客观指标（可自动/半自动采集）

| 指标 | 定义 | 采集方式 |
|------|------|----------|
| 任务成功率 | 满足全部验收条件的任务数 / 总任务数 | 测试框架断言 |
| 约束满足率 | 满足的显式约束数 / 总显式约束数 | 逐条断言 |
| 记忆检索准确率 | 检索返回的相关记忆数 / 返回总数 | 人工标注 gold set |
| 记忆使用有效率 | 检索后实际影响输出的记忆数 / 检索命中数 | 输出 diff 分析 |
| 计划执行完成率 | 计划中完成的步骤数 / 计划总步骤数 | 任务树状态 |
| 工具调用成功率 | st=success 的 tool_call 数 / 总 tool_call 数 | stats.jsonl 聚合 |
| 故障恢复成功率 | 注入故障后恢复并完成的任务数 / 注入故障任务数 | 故障注入测试 |
| 错误结果识别率 | 正确识别为错误的失败调用数 / 实际失败调用数 | 对照 ground truth |
| 平均任务成本 | 单任务 token 消耗 / 墙钟时间 | usage 统计 |
| 长任务状态保持率 | 长任务 checkpoints 中状态一致的步数比例 | checkpoint 对比 |

### 3.2 人工评审指标（无法可靠量化时）

| 维度 | 评分标准（1–5） |
|------|----------------|
| 计划合理性 | 1=完全不可行；3=可行但冗余/低效；5=步骤最优且考虑风险 |
| 经验复用质量 | 1=引用无关/错误经验；3=引用相关但未有效利用；5=精准引用并正确应用 |
| 失败归因准确性 | 1=错误归因；3=定位到模块但未到根因；5=根因正确且修复建议可行 |

人工评审必须双评（或单评+抽样复核），分歧 >1 分时第三人仲裁。

## 4. 测试集结构

测试集 ID 规则：`EVAL-{类别}-{序号}`，类别 ∈ {BASE, MULTI, MEM, XSESS, AGENT, FAULT, LONG}

| 类别 | 覆盖 | 案例数（V1） |
|------|------|-------------|
| BASE | 基础单步能力 | 8 |
| MULTI | 多步骤任务 | 6 |
| MEM | 长期记忆 | 6 |
| XSESS | 跨会话 | 4 |
| AGENT | 多智能体协作 | 4 |
| FAULT | 故障恢复 | 5 |
| LONG | 长任务连续性 | 4 |
| **合计** | | **37** |

每个案例必须包含：唯一编号、目标、输入与环境条件、预期行为、评分标准、（执行后）结果、证据位置。详见 `F-BENCHMARK-DATASET.md`。

## 5. 版本基线机制

### 5.1 基线锚点（每次基准运行必须记录）

```yaml
baseline_id: BL-{date}-{version}
code_commit: {sha}
tag: {git tag or null}
binary_sha256: {if applicable}
model: {model-id from config}
model_config: {temperature, max_tokens, ...relevant}
tool_permissions: {allowed_tools list}
environment: {os, cwd, plugin list}
c1_gates: {enabled, c1, soft_limit, hard_limit}
run_timestamp: {ISO8601}
```

### 5.2 版本对比规则

- 仅当 5.1 中 model / tool_permissions / environment 三项一致时，两次结果可直接数值比较。
- 任一项变化 → 结果标注"环境不同，不可直接比较"，需 A/B 或控制变量重跑。
- 代码升级 + 环境不变 → 可归因于系统升级。

### 5.3 成长报告模板

每次重要升级后输出：

```
## 能力成长报告 {upgrade_name}
- 基线: BL-old → BL-new
| 维度 | 旧值 | 新值 | Δ | 显著性 |
|------|------|------|---|--------|
| D1 任务理解 | … | … | … | … |
| …  | … | … | … | … |
- 退化项：…
- 成本变化：…
- 新增风险：…
```

## 6. 执行流程

1. **冻结环境**：按 5.1 记录锚点。
2. **顺序执行**：按测试集 ID 顺序跑，每案例独立 session。
3. **证据落盘**：原始输入/输出/工具调用日志存 `evidence/EVAL-{id}/`。
4. **评分**：客观指标自动算；人工指标按 3.2 评。
5. **报告**：汇总到 `G-BASELINE-RESULTS.md`。

## 8. 已知限制

1. **模型不可控**：同测试在不同模型上结果不可比——基线必须锁模型。
2. **主观维度**：D3/D6 部分指标依赖人工评审，跨评审者一致性需持续校准。
3. **成本**：完整 37 案例一轮约 X token / Y 分钟（首轮跑完后补充实测值）。
4. **C1 依赖**：工具成功率指标依赖 stats.jsonl 完整性；L2 跳过导致 bash 失败率虚低（已知偏差，报告需注明）。
