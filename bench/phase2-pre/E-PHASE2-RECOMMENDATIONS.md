# Phase 2 建设建议

任务编号：EC-PHASE2-PRE-01 / WP-02 交付物 E
审计日期：2026-10-31
性质：建议与优先级排序，**不启动实施**（待项目负责人审批）

---

## 建设方向总览

基于审计实测：Immune V1 已冻结且闭环；记忆/神经/执行已实现；代谢与稳态部分实现；认知依赖上游循环无自研层。Phase 2 建议聚焦「巩固成果 → 补观测缺口 → 强执行可靠性 → 成本可见」四步，而非铺开新系统。

---

## 方向 1：V1 工程化巩固（冻结加固包）

| 维度 | 内容 |
|------|------|
| **当前缺口** | V1 无 freeze commit/tag，仅工作区+哈希锚点；SDK 类型手改将被 regen 覆盖（D-N1）；classify 未入 barrel；重建缺 channel=local 双保险 |
| **建设价值** | 保护已验收资产；消除升级/重建时的静默回退风险；让"V1 冻结"从文档状态变成仓库状态 |
| **前置依赖** | 无（纯工程操作） |
| **实施复杂度** | **低**（1–2 个工作日）：归档 commit/tag + regen patch 流程 + barrel 导出 + 构建 SOP 文档 |
| **预期收益** | 上游同步冲突面可预期；新机器可复现构建；SDK 消费方类型完整 |
| **验收标准** | ① 仓库存在 V1 tag/commit 且工作区干净；② 执行 regen 后 agentID/diagnostic 类型仍在（patch 流程验证）；③ `@/metrics/barrel` 可导入 classifyToolError；④ 按 SOP 重建的二进制通过 C4/C2 基线且 channel=local |

## 方向 2：诊断链路补全（Immune V2 接线）

| 维度 | 内容 |
|------|------|
| **当前缺口** | 远程上报不转发 diagnostic/agentID（D-N6）；ModelCall.diagnostic 空置（D-N4）；tool_not_found 生产不可达（D-N2）；LLM/API 错误无 7 字段结构化 |
| **建设价值** | V1 只覆盖工具错误；LLM 层失败（余额、限流、超时）是实际高频故障源，当前只有 kind=llm 粗分类。补齐后免疫系统才覆盖完整故障面 |
| **前置依赖** | 方向 1（先固化再扩展）；LLM 错误分类规则设计（复用 classify 三态框架） |
| **实施复杂度** | **中**（3–5 个工作日）：classify 增 LLM 分支 + processor session.error 接线 + subscriber 转发 + 单测/E2E |
| **预期收益** | ev:error 覆盖 tool+llm 两类；远程分析与本地账本诊断一致；错误预算可按类别聚合 |
| **验收标准** | ① 注入 LLM API 故障（mock）→ ev:error 带 7 字段且 error_class=llm_api；② subscriber 上报含 diagnostic；③ V1 工具错误回归 43/43 + C4/C2 基线不变（不破坏冻结契约） |

## 方向 3：执行可靠性补强（观测口径诚实化）

| 维度 | 内容 |
|------|------|
| **当前缺口** | bash 非零退出不发 error ToolCall（D-L2）→ 成功率虚高；PS 非终止错误记 success（D-L2）；slice_post 重启窗口缺失（D-L1）；账本轮转仅 1 代（D-N5） |
| **建设价值** | 观测系统的价值取决于口径诚实。当前"成功"包含真实失败，任何基于账本的健康判断都被污染；这是 Phase 3 自治能力建设的地基 |
| **前置依赖** | 与方向 2 可并行；需 A/B 设计（口径变更会改变历史可比性——账本标注 schema_version 或双轨过渡） |
| **实施复杂度** | **中-高**（5–8 个工作日，含 A/B 与账本迁移策略）：exit≠0 发 error 事件 + PS error stream 检测 + sliceStack 重启断代 + 轮转多代 |
| **预期收益** | 账本成功率反映真实；Immune 分类覆盖执行失败全谱；重启后归因快速恢复 |
| **验收标准** | ① 构造 exit=1 命令 → ev:tool st=error + ev:error 带诊断；② PS Write-Error 场景被拦截；③ 杀进程重启后 60s 内 tid 归因准确率回到基线；④ 账本保留 ≥7 天可查 |

## 方向 4：成本可见化与 Token 预算执行

| 维度 | 内容 |
|------|------|
| **当前缺口** | 账本无 cost 字段（D-L3）；无预算执行器——compaction 只管上下文长度不管累计消耗；serial 实验已量化 Token 结构（88% cache）但无持续采集 |
| **建设价值** | Token 预算已技术可行（数据齐）；长期会话/子代理风暴的成本需要闸门。货币口径可后置（依赖 provider 账单 API 决策） |
| **前置依赖** | 方向 3（先让账本口径诚实，再往里加钱字段才有意义）；模型单价表维护机制 |
| **实施复杂度** | **低-中**（2–4 个工作日）：ev:model 增 estimated_cost + 会话/日预算配置 + 超限策略（warn/block/降级小模型） |
| **预期收益** | 会话级成本可查；预算护栏防止 runaway 子代理；为对公部署提供成本报表原料 |
| **验收标准** | ① stats.jsonl ev:model 含 cost 字段且与 DB message.cost 对账偏差 <5%；② 设置低预算触发 warn 日志；③ 超限 block 路径有 E2E |

## 方向 5（观察项·暂不建议投入）：架构减负

- **内容**：prompt.ts 巨石拆分（SP1）、Metrics 三路径 publish 收敛（R4）
- **判断**：**技术债真实但当前无业务痛点驱动**。拆分巨石回归成本极高（上游同步更痛苦），建议仅在方向 1–3 中顺手做局部整理（如抽 publish helper），不做主动重构立项。重新评估触发条件：上游大版本重构 prompt.ts 时被动获得拆分窗口。

## 优先级排序

| 序 | 方向 | 理由 |
|----|------|------|
| **P0** | 方向 1：V1 工程化巩固 | 成本最低、保护既有成果、是其他一切的前置；不先做则方向 2 的改动也无处安放 |
| **P1** | 方向 2：诊断链路补全 | 免疫系统完整性的直接缺口；LLM 故障是现实高频源；与 V1 框架同构可平滑扩展 |
| **P1.5** | 方向 3：执行可靠性 | 与方向 2 互补（tool 完整性 × llm 完整性）；A/B 设计可与方向 2 共用方法论 |
| **P2** | 方向 4：成本可见化 | 依赖方向 3 的口径诚实；货币字段可作为独立小迭代 |
| **—** | 方向 5：架构减负 | 仅被动触发，不排期 |

**排序原则**：先固化（1）→ 再补全故障覆盖（2、3）→ 后增强经济性（4）；每步以回归基线不破坏为硬约束，符合 V1 冻结规则「新能力入 V2、不改 V1 契约」。
