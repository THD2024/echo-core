## 2. B1–B6 任务定义

### B1：简单任务

**任务**：修改一个常量并验证。

具体：在测试仓库 `bench/repo-b1/` 中创建 `config.js`，初始内容 `const RETRY_LIMIT = 3;`。任务提示词：「把 config.js 中的 RETRY_LIMIT 从 3 改成 5，然后运行 `node -e "require('./config.js')"` 确认没有语法错误。」

**成功判定**：
- 文件内容变为 `const RETRY_LIMIT = 5;`
- 验证命令执行成功
- 模型调用次数 ≤ 4

**考察**：效率、不把简单任务复杂化、空轮

---

### B2：多步骤任务

**任务**：统计并报告。

具体：在测试仓库 `bench/repo-b2/` 中放置 5 个 JSON 文件（模拟日志）。任务提示词：「统计这 5 个 JSON 文件中每个文件的记录数，然后在 `report.md` 中生成一个表格，列出文件名和记录数，最后加一行总记录数。」

**成功判定**：
- `report.md` 存在且包含 5 行文件数据 + 1 行汇总
- 记录数与实际一致
- 模型调用次数 ≤ 10

**考察**：规划、持续推进、收口

---

### B3：多文件代码修改

**任务**：一处改动波及多文件。

具体：测试仓库 `bench/repo-b3/` 中有 `utils/math.js`（导出 `add`/`sub`）、`utils/math.test.js`（测试文件）、`index.js`（引用 math）、`README.md`（API 文档）。任务提示词：「在 utils/math.js 中新增一个 `multiply(a, b)` 函数，在 utils/math.test.js 中为它添加测试，在 index.js 中导出它，在 README.md 的 API 表格中添加一行。」

**成功判定**：
- 4 个文件全部修改
- `node utils/math.test.js` 通过
- `multiply` 在 index.js 中可 require
- 模型调用次数 ≤ 15

**考察**：上下文组织、结果验证、修改范围准确性

---

### B4：工具密集型任务

**任务**：需要大量搜索/读取操作。

具体：测试仓库 `bench/repo-b4/` 中有 30 个 `.js` 文件，每个导出不同函数，其中 5 个文件包含 TODO 注释。任务提示词：「搜索所有包含 TODO 注释的文件，列出每个文件中 TODO 的完整内容和行号，汇总到 `todos.md`。」

**成功判定**：
- `todos.md` 包含恰好 5 个文件的 TODO
- 行号正确
- 无遗漏、无多余
- 模型调用次数 ≤ 25

**考察**：工具选择准确性、搜索效率、无效往返

---

### B5：失败恢复任务

**任务**：可控故障注入。

变体（每个至少 1 例）：
- **B5a**：任务要求运行一个不存在的命令，观察是否识别错误并改用正确路径
- **B5b**：任务要求编辑一个不存在的文件，观察是否报告而非静默失败
- **B5c**：任务要求调用一个不存在的工具名，观察错误处理

**成功判定**：
- 错误被正确识别（不静默通过）
- 不重复相同失败路径 ≥ 3 次
- 最终状态明确（成功或明确失败，不悬挂）

**考察**：失败可观测、恢复策略、错误分类

---

### B6：历史经验复用任务

**任务**：重复执行同类任务两次。

具体：第一次执行 B3 任务（记录完整过程）。然后清空会话上下文，用稍有不同的措辞再次要求执行相同的 B3 任务（如「给 math 模块添加 divide 函数及其测试」）。

**成功判定**：
- 第二次任务调用次数 ≤ 第一次的 80%
- 第二次 token 消耗 ≤ 第一次的 85%
- 第二次结果质量不低于第一次

**考察**：记忆降本、经验复用、避免重复踩坑

---

## 3. 重复测试规范

- 每类任务至少执行 **3 次**
- 每次使用**新会话**（不共享上下文）
- 记录每次独立结果 + 平均值 + 中位数
- 不选择最好结果，报告全部

**预算估算**（基于 Phase 0 每次调用 ~100K input token）：
- B1: 3 次 × ~4 调用 × ~50K tokens ≈ 0.6M tokens
- B2: 3 次 × ~8 调用 × ~80K tokens ≈ 1.9M tokens
- B3: 3 次 × ~12 调用 × ~100K tokens ≈ 3.6M tokens
- B4: 3 次 × ~20 调用 × ~100K tokens ≈ 6.0M tokens
- B5: 3 变体 × 3 次 × ~6 调用 × ~80K tokens ≈ 4.3M tokens
- B6: 2 轮 × 3 次 × ~12 调用 × ~100K tokens ≈ 7.2M tokens
- **合计 ≈ 23.6M input tokens** ≈ ¥4–8（DeepSeek Flash 定价）

## 5. 执行流程

```
1. 创建测试仓库 bench/repo-b{1..4}/
2. 准备任务提示词文件 bench/tasks/b{1..6}.md
3. 对每类任务：
   a. 记录 stats.jsonl 当前行号
   b. 开新会话，粘贴任务提示词
   c. 等待执行完成
   d. 记录 stats.jsonl 新增行
   e. 运行验证命令
   f. 保存结果到 bench/results/
4. 用脚本聚合数据
5. 生成基线报告
```

## 7. 注意事项

1. **不把任务结束当任务成功**——必须运行验证命令
2. **不选最好结果**——报告全部 3 次
3. **C1 事件可能不全**——进程重启前旧代码不产生 C1 事件；协议设计为兼容两种情况（无 C1 时部分指标标记为"不可用"）
4. **测试仓库独立**——bench/repo-* 与正式项目完全隔离
5. **预算监控**——每完成 2 类任务检查一次累计 token 消耗
