## 方案 A：分层混合记忆架构（Layered Hybrid Memory, LHM）

### 核心理念

借鉴 CLS（互补学习系统）双系统理论 + MemGPT 分层 + Graphiti 时序图，将记忆分为**工作层 / 情景层 / 语义层 / 程序层**四层，每层独立存储与检索，通过巩固管道跨层流动。

### 数据流

**写入流**：
```
Agent 行动 → 写入门控(surprise/utility评分) → 情景层追加
                                            → 实时抽取实体/关系 → 语义层
                                            → 成功路径检测 → 程序层
```

**读取流**：
```
Query → 混合检索(BM25+向量+图+时间) → 候选集
      → 后检索装配(去重/冲突/陈旧/组包) → 证据包 → Agent
```

**巩固流**（离线/空闲）：
```
情景层高价值事件 → LLM 反思 → 语义摘要/规则 → 语义层/程序层
语义层冲突审计 → supersede/revoke → 版本更新
全局衰减扫描 → 低价值降权/归档
```

### 优点
- 职责清晰，每层可独立优化
- 符合认知科学双系统理论
- 巩固管道可审计、可回滚
- 与现有 MiMoCode Memory 系统兼容性好（可渐进迁移）

### 缺点
- 四层间数据流复杂，需要精心设计接口
- 巩固管道的 LLM 调用成本需要控制
- 图构建与维护是额外工程负担

## 方案 B：统一记忆图架构（Unified Memory Graph, UMG）

### 核心理念

借鉴 Graphiti 时序知识图 + A-MEM Zettelkasten + HippoRAG PPR，将**所有记忆统一表示为带时间戳和版本的节点-边图**，通过图遍历和 PageRank 实现关联检索，通过版本链实现冲突管理。

### 数据流

**写入流**：
```
Agent 行动 → 图写入 API
           → 创建 Event 节点 + 时间戳
           → 实体抽取 → Entity 节点 + RELATES 边
           → 因果检测 → CAUSES 边
           → 与已有事实冲突 → SUPERSED 旧节点
```

**读取流**：
```
Query → 实体识别 → 图锚点
      → PPR 扩散（HippoRAG 式关联补全）
      → 混合排序（PPR + BM25 + 向量 + 时间衰减）
      → 版本过滤（只取 active 节点）
      → 证据包组装 → Agent
```

**巩固流**：
```
离线：冲突审计 → 标记 SUPERSED
      衰减扫描 → 降权/归档
      图重构 → 合并冗余节点
```

### 优点
- 单一数据模型，查询表达力强
- 天然支持多跳、因果、时序
- HippoRAG 已验证 PPR 路线有效
- Graphiti 已验证时序版本化可行

### 缺点
- 图构建与维护成本高（LLM 抽取每条边）
- 写入延迟高（A-MEM O(N²) 问题）
- 与现有文件式 Memory 系统差异大，迁移成本高
- 单一图结构可能不如分层灵活

## 方案对比表

| 维度 | 方案 A (LHM) | 方案 B (UMG) |
|------|-------------|-------------|
| **数据模型** | 四层分离 + 统一总线 | 单一图 + 版本链 |
| **写入延迟** | 低（只写情景层，异步抽取） | 高（每条都需图更新） |
| **检索表达力** | 中（需跨层融合） | 高（图遍历天然多跳） |
| **冲突管理** | 版本化 + supersede | SUPERSED 边 + 版本链 |
| **巩固成本** | 中（离线管道） | 低（图已结构化） |
| **与现有系统兼容** | 高（可渐进迁移） | 低（需重建数据层） |
| **工程复杂度** | 中 | 高 |
| **认知科学对应** | CLS 双系统 | 索引理论 + 展布激活 |
| **生产验证** | MemGPT + Graphiti 混合 | Graphiti + HippoRAG |
| **可扩展性** | 好（各层独立扩展） | 中（图规模受限） |

## 取舍分析

### 选择方案 A 的场景
- 需要与现有 MiMoCode Memory 系统平滑过渡
- 写入频率高、延迟敏感
- 团队对图数据库经验有限
- 希望各层可独立演进

### 选择方案 B 的场景
- 多跳推理、因果查询是核心需求
- 愿意投入图构建的 LLM 成本
- 数据量适中（<100 万节点）
- 需要统一的查询接口

### 混合建议

实际最优解可能是 **A 为骨架、B 为语义层实现**：
- 情景层用方案 A 的不可变日志
- 语义层用方案 B 的时序知识图
- 程序层用方案 A 的 skill 库
- 巩固管道同时服务两层

这样兼顾了写入效率（情景层轻量）和检索能力（语义层图遍历）。
